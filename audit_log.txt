ISSUE #1: null-mapped "num_of_provinces_owned_or_owned_by_*_subjects_with"
          (439 missions affected - HIGHEST SEVERITY)
================================================================================

The triggers `num_of_provinces_owned_or_owned_by_non_sovereign_subjects_with`
and `num_of_provinces_owned_or_owned_by_subjects_with` are explicitly mapped
to null in triggerToText. This means the ENTIRE condition is suppressed from
display, even though these triggers contain real player-facing requirements.

These are nearly identical in function to `num_of_owned_provinces_with` (which
IS handled) -- they just also count provinces owned by subjects.

Full dataset count: 439 missions (84 found in 20% sample)

Examples:

  Mission: Y65_integrate_the_expedition (Integrate The Expedition)
  Raw: num_of_provinces_owned_or_owned_by_non_sovereign_subjects_with = {
         value = 40
         region = lupulan_rainforest_region
         NOT = { religion = accretive_path ... }
       }
  Current display: NOTHING (entire condition suppressed)
  Should display: "You or subjects own at least 40 provinces
                   (in lupulan rainforest region, not following certain religions)"

  Mission: A31_elven_history (Pieces of Elven History)
  Raw: num_of_provinces_owned_or_owned_by_non_sovereign_subjects_with = {
         value = 1
         trade_goods = precursor_relics
       }
  Current display: NOTHING
  Should display: "You or subjects own at least 1 province (produces precursor relics)"

  Mission: eord_2_silence_cacophony (Silence and Cacophony)
  Raw: num_of_provinces_owned_or_owned_by_non_sovereign_subjects_with = {
         value = 10
         region = haraf_region
       }
  Current display: NOTHING
  Should display: "You or subjects own at least 10 provinces (in haraf region)"

FIX: Implement a handler similar to num_of_owned_provinces_with but prefixed
     with "You or subjects own...".

development, etc.) but misses many others. When the inner condition isn't

qualifying condition that specifies WHICH provinces.

ISSUE #5: Complex country tag scopes not fully resolved
          (183 instances in 20% sample, ~915 total - MEDIUM SEVERITY)
================================================================================

Country tag scopes (e.g. F39 = { ... }) with complex inner conditions
that don't match the known inline patterns (is_subject_of=ROOT,
alliance_with=ROOT, exists=yes/no, etc.) are either dropped or
shown as raw text.

The parser handles the 8 most common inline patterns well. But multi-line
blocks with conditions like custom if/else logic, has_opinion_modifier,
nested NOT blocks, or overlord scopes are not fully resolved.

Examples:

  Mission: tluukt_curtail_liberators (Curtail Liberators)
  Raw: F39 = { NOT = { is_subject_of_type = tributary_state_anb } }
  Current: probably dropped (complex nested NOT inside country scope)
  Should: "F39 is not a tributary state"

  Mission: exwes_claiming_the_small_country (Claiming the Small Country)
  Raw: A12 = { if = { limit = { is_subject_of = PREV }
               has_opinion = { who = ROOT value = 100 } } }
  Current: probably dropped (if/limit block inside country scope)
  Should: "A12 has opinion of us at least 100 (if subject of us)"

FIX: For the most common sub-patterns (is_subject_of_type, is_at_war,
     religion, government, total_development, etc.), add more inline
     pattern matchers in the country tag scope handler.

--- NEW ISSUE 1.1: calc_true_if uses global regex — wrong amount for 2nd+ blocks
  Severity: MEDIUM (103 missions with multiple calc_true_if blocks)
  File: build_html.py line 1953
  Code: const amountMatch = processed.match(/calc_true_if\s*=\s*\{[\s\S]*?amount\s*=\s*(\d+)/);
  Problem: This searches the ENTIRE `processed` text, not just the current
    block. When a mission has 2+ calc_true_if blocks with different amounts,
    the 2nd+ block will incorrectly display the FIRST block's amount.
  Example: A mission with calc_true_if{amount=2} followed by calc_true_if{amount=5}
    would show "At least 2 of the following:" for BOTH blocks.
  Fix: Track position in processed text, or extract amount from the current
    line's val instead of re-searching the whole document.

--- ISSUE 3.1: 592 modifiers still have EU4 color codes in their names
  Severity: MEDIUM
  File: modifiers_data.json (data source level)
  These are primarily "Adventurers Wanted!" province modifiers using codes
  like "section-Y(...) section-! section-g...section-! section-O...section-!"
  The build_html.py modRef() function (line 3093) strips these at display time:
    const name = rawName.replace(/section[A-Za-z!]/g, '');
  So the DISPLAY is correct, but the raw data is noisy. These modifiers
  show correctly in the UI because the strip happens at render time.
  Status: Display is fine. Data-level cleanup would be nice but not critical.

--- ISSUE 3.2: Liberty Desire and similar modifiers show extreme percentages
  Severity: HIGH
  File: modifiers_data.json (pre-computed by parse_modifiers.py)
  424 modifiers have percentage values exceeding 500%.
  Examples:
    brambleskinner_loyal_vassal: Liberty Desire in Subjects = -5000%
    bagcatir_vassal_rebellion:   Liberty Desire = -2500%
    salla_cenag_heartsmitten:    Chance of New Heir = -100000%
    I98_3015:                    Naval Morale = +75%  (this one is correct)
  Root cause: In parse_modifiers.py, liberty_desire and heir_chance are in
    the percent_keys set. EU4 stores these as whole numbers (e.g., -50 means
    -50 liberty desire points), but format_value_nice() multiplies by 100,
    producing -5000%. The game displays these as flat values (e.g., "-50").
  Affected keys: liberty_desire, reduced_liberty_desire, heir_chance
  Fix: Move liberty_desire, reduced_liberty_desire, and heir_chance out of
    percent_keys in parse_modifiers.py, or add special-case handling to
    treat them as flat values when abs(value) >= 1.
